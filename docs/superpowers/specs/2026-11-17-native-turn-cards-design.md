# 原生单轮问答卡片：设计与可行性

日期：2026-11-17。基线：主分支 0.6.4，提交 `d78fe74`。开发分支：`feat/native-turn-cards`。状态：设计待确认，本次不修改运行代码或已安装产物。

## 目标与默认决策

一个卡片仍表示用户的一次提问及由它发起的 Agent 回答过程。卡片里的 Agent 区域应展示 DSH 原生可见的过程，包括流式文字、运行状态、工具调用与结果、提问及权限处理。保留原生右侧完整对话与祖先路径阅读。

默认卡片改为 **640 × 360px，16:9**，最小建议为 480 × 270px。比例用于默认尺寸，手动调整不锁定比例。已有手动尺寸保留；未设置手动尺寸的旧卡片应用新默认尺寸时，使用现有避让器修复相邻重叠，不重置整树布局和视角。需要统一节点样式、首次测量、布局及避让器的默认尺寸来源，避免多处常量不一致。

生成过程中卡片外框保持固定尺寸，内容在内部滚动，文字增加不推动整棵树。读者原本位于底部时跟随最新内容；向上阅读后暂停跟随，并提供回到最新内容的入口。缩放继续只改变显示比例，不触发正文隐藏或自动折叠。

## 当前实现为何不完整

当前 `StudyPage.tsx` 的卡片正文为插件自己的 Markdown 组件。`Study.watch()` 订阅 Session 事件，约每 100ms 调用 `readTurn()` 拼接文字；它不是刻意等待整轮结束才显示，但也没有复用完整原生 Chat 装配和展示状态。

`readTurn()` 只读取 `text-delta` 和最终 Assistant 消息，不展示工具、推理/分析状态、重试、等待输入等节点。DSH 的 transient 流片段与最终消息在 Step 完成前可能同时保留，单纯追加两者会重复正文。已用符合该契约的最小事件序列检查：流片段为「先确认文件结构。」，最终消息仍为该句，现有函数输出两遍。多 Step、重试、断线恢复及 partial 转正都需按原生装配语义处理。这个检查证明去重缺口，不足以单独断定用户现场所有流式延迟的原因；还需真实分段输出回放。

另一个问题可以直接从实现确认：卡片生成时 `endSeq` 尚为空，下一轮输入组件不会准备 fork，但卡片仍挂载输入座位，最终显示大块「等待当前回答结束…」占位。它应由运行状态和当前请求的交互区替代，而非伪装成不可用输入框。

目前只复用 `conversation.composer.bar`；原生提问和审批注册在 **`conversation.composer` chain**。因此复制 InputBar 不能带来提问表单。现有卡片输入还绑定父轮结束后准备的下一轮 fork，不能用这个草稿会话回答当前仍在运行的会话请求。

## 三种方案

| 方案 | 成本与限制 | 结论 |
| --- | --- | --- |
| 在自制 Markdown 上补过程和表单外观 | 初期文字修复较快，但需自己维护工具状态、提问语义及更多宿主功能 | 不作为长期方案 |
| 使用 DSH 本轮数据与原生节点组件，卡片拥有本轮容器和单一交互入口 | 需单轮过滤、Session 绑定和交互路由，能够共享宿主的展示与动作 | 推荐，先验证一张卡片 |
| 每张卡片挂载完整原生会话页面 | 会反复挂载祖先历史、导航和输入，容易出现重复编辑器、重复面板和滚动竞争 | 不采用 |

这里的「复用原生」是复用实际注册组件、事件装配和提交动作，不复制一套相似 CSS 或私有源文件。Slot 适配仍限定 DSH 0.2.2-rc.3；没有验证前，不承诺纯插件能复用每个组合行为，也不承诺完全没有性能增量。

## 卡片的状态设计

标题仍显示问题、引用来源及紧凑状态；Agent 正文不重复显示顶部已经存在的原始用户问题。原生过程区遵循 DSH 的详情折叠偏好。

| 状态 | 卡片正文 | 底部与交互 |
| --- | --- | --- |
| 准备会话 | 紧凑的准备状态 | 不显示大块灰色伪输入框 |
| 正在生成 | 原生流式文字、分析状态及工具过程；已输出内容保留 | 紧凑运行控制、停止生成；不准备下一轮 fork |
| 执行工具 | 工具摘要与按需展开的详情、结果和错误 | 沿用当前运行会话的停止动作 |
| 等待用户 | 已产生内容继续可读 | 在当前卡片内显示原生提问、计划确认或审批面板 |
| 完成 | 原生本轮内容与工具过程，按 DSH 偏好折叠 | 恢复已有悬浮追问输入框，按本轮结束处准备子分支 |
| 停止或失败 | 保留已输出文字、过程与原生错误状态 | 提供经验证的停止/重试或继续入口，不当作正常完成 |

较长提问表单在卡片内部使用独立可滚动面板，保留固定操作区。必要时暂时接管底部交互空间，正文保留可访问位置；不强行自动扩大卡片破坏 16:9 默认与邻居布局。手动放大仍可用。未知扩展交互若不能在卡片适配，保留原生入口并提示待处理，不静默丢弃。

待交互请求优先于普通完成态和下一轮输入。尤其在工具超时后继续运行的模式下，单个 DSH Turn 已结束不一定意味着没有待答问题，不能只凭 `endSeq` 或当前持久化的 `status` 隐藏交互。

## 数据与渲染边界

建议增加按节点管理的 `TurnPresentation`，从 DSH 的 Conversation/Chat 快照读取本轮投影，区分文字、过程、待交互、结束及错误。用 Session、真实 Turn、Step、attempt 与原生节点 key 关联，不按卡片显示序号或最后一条 Assistant 消息猜测。

已核对的接入点：

- `ChatSnapshot.locations.getTurn()` / `getStep()` 提供按轮次和步骤的节点索引。
- `ChatSnapshot.nodes.source(key)` 提供稳定的按节点订阅；原生 `assistant-step` 同时支持 running、settled 和 interrupted。
- `conversation.chat.flow` / `conversation.chat.node` 提供原生消息和工具展示注册。
- `uiSession.pendingInteractions` 提供按 Session 的待交互状态；`conversation.composer` 提供提问与审批的原生表单路由。

这些契约证明存在可复用的基础，但不能只把 `getTurn()` 的 key 塞进完整 ChatView 就算完成。原生分组可能跨步骤甚至跨轮次，ChatFlow 的运行状态和尾部也按会话最新轮次计算；单轮适配必须核对分组成员、状态、折叠上下文、文件/代码动作、字典与 Store scope，避免旧卡片显示另一个轮次的运行状态或继承历史。

原生展示区需要独立样式边界，排除插件现有的通用按钮重置等样式，沿用原生排版和工具控件的样式。不能让原生工具按钮因置于 `.st` 下而重新被卡片的通用按钮样式覆盖。原生组件通过运行时注册与公开契约复用，分发包不依赖同级 DSH 源码路径。

完成后的历史正文、导出与引用定位共用同一本轮展示数据。划词只针对 Assistant 可见正文，不能把工具输出、状态标签或操作按钮串入引用文本。需保留跨块选区、进入输入框后的高亮和返回来源锚点。

## 提问、审批与右侧对话

交互必须使用**当前运行 Session**。普通下一轮草稿仍使用原来独立的精确边界 fork，两者不可混用。

优先验证单一交互面板的展示位置路由：在当前选中的运行卡片中展示原生 `conversation.composer` 选出的面板，复用原 main Session 绑定和动作，避免额外创建问题请求或第二个编辑器。右侧保持原生对话内容，待处理面板在卡片和传统界面之间只有一个可编辑实例；退出画布或无法展示时恢复宿主原生位置。候选实现是通过插件自有 slot 别名加 Portal 路由原生选出结果，必须排除自身注册防止递归，并在卸载时解除接管。

不能只另建一个 SessionProvider 后复制表单：前台请求认领、优先级、超时、断连和单一响应都由宿主管理，需要验证其生命周期。切换卡片时保存交互草稿，不将 A 的问题显示或提交给 B；非当前卡片出现待处理状态时标记对应节点，不强行抢走当前阅读位置。右侧隐藏时也必须能在当前卡片完成答复。

Agent 的澄清问题及审批答复属于其任务过程，不因点击「提交答案」自动建学习子节点；用户主动发起新的追问才建子节点。DSH 同时有阻塞型提问和超时后继续、稍后答复的形式：先验收阻塞型；若后者将答复放到后续 DSH Turn，需按 `callId` 与消息来源关联，再决定是否增加 `relatedTurns` 等兼容元数据，不能用单一 `endSeq` 硬截断，也不能误把系统关联答复当作用户新分支。这是需要验证的范围，不能提前宣称所有模式都已支持。

## 性能约束

- 使用共享原生装配结果，按本轮/原生节点 key 订阅；token 不再通过全局 `Study.emit()` 使所有卡片消费新的全局上下文。
- 文字更新只影响对应卡片及实际需要更新的右侧消息，不重建 React Flow 节点、连线、尺寸或坐标。
- 初期优先在当前卡片及运行卡片验证原生渲染，历史完成内容使用缓存；工具详情和大型结果按需加载。不可见节点可暂停视图工作，但数据继续接收，恢复显示最新状态；不按缩放比例移除可见卡片正文。
- 保留固定卡片外框、内部滚动、现有背景纹理及缩放缓存策略。计划以 50–100ms 量级合并呈现变化，最终值以原生流处理和实测为准；不额外复制整份祖先会话 DOM。
- 与 0.6.4 用相同节点、文本和手势做三轮对照，检查前台帧间隔、长任务、更新范围及内存。稳定可复现的性能回退不能以「原生组件必然更快」解释掉；出现回退时先缩小实时挂载范围或改进订阅，再扩大接入。离屏/无头测试不能代替用户前台的流畅度。

## 分阶段实施与验证门槛

1. **基础尺寸与流式修复。** 统一默认尺寸；改正准备/生成/等待/完成状态，去掉生成时灰色伪输入框；验证客户端已经收到分片时能够在结束前持续显示。用延迟分段模型测试纯文本、多 Step、重试、partial 转正、重连和停止，保证正文不重复、不回退、不丢段。首个可见更新目标为收到客户端分片后约 150ms 内，不包含模型与网络耗时。
2. **原生本轮显示验证，再扩展。** 先做一张卡片的原生渲染实验，核对文字、工具摘要/详情、状态、文件和代码入口，只有自己的本轮及相关过程；保留右侧完整祖先路径。通过独立隔离配置的对照后再替换正式卡片正文。若公共契约不足，记录最小宿主扩展点并讨论，不复制整个私有 ChatView 兜底。
3. **提问/审批接入。** 先验证一次阻塞提问的卡片内回答、模型恢复、停止和表单草稿，再验证多问题、计划确认、权限允许/拒绝、切卡、关闭右侧与多窗口去重。超时后继续、迟到答复及其跨轮次关系单独验收，必要时先讨论范围和数据迁移。

每阶段保留可回退到 0.6.4 显示路径的能力，使用既有真实会话和引用兼容检查。最小端到端案例为：流式文字 → 工具执行 → Agent 提问 → 卡片内回答 → 模型继续流式回答 → 完成后追问生成一个子节点；过程中关闭右侧后仍能完成提问，原生路径中历史只出现一次。另用约 20 张完成卡片与两张运行卡片进行性能对照。
